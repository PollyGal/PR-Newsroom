# CLAUDE.md — PR-ньюсрум «Валькирии»

Мультиагентный PR-конвейер для PR-специалиста бренда: находит инфоповоды,
переупаковывает материал под СМИ с проверкой уникальности и оценивает
медиаэффективность публикаций в PR Points. Три субагента, объединённых
в один проект, и статический дашборд над их результатами.

## Агенты

1. **Хильда** (`.claude/agents/hilda.md`) — newsjacking-скаут. Находит и
   приоритизирует поводы, готовит брифы, шлёт сводки на почту.
2. **Сага** (`.claude/agents/saga-adapter.md`) — адаптер под 4 СМИ
   (Forbes Russia, РБК Компании, Инк, Setters Media) с проверкой уникальности
   через text.ru.
3. **Фрейя** — пайплайн PR Points из трёх ролей:
   `pr-analyst` (анализ) → `pr-calculator` (расчёт) → `pr-reporter` (отчёт).

ВАЖНО: субагенты не вызывают друг друга. Последовательность шагов оркеструешь
ТЫ (главная сессия) по командам ниже.

## Команды вызова

Агенты реагируют на обращение по имени.

### Хильда (поиск поводов)
- **«Хильда, найди поводы по теме X»** / «Хильда, сделай sweep» — сканирование
  медиаполя, квалификация по чек-листу, брифы с приоритетом в `output/briefs/`.

### Сага (адаптация под СМИ)
- **«Сага, адаптируй бриф <id>»** — берёт бриф, делает 4 версии под СМИ,
  проверяет уникальность через text.ru, сохраняет тексты + `summary.json`.

### Фрейя (оценка эффективности)
- **«Фрейя, проверь статью <файл>»** — одна публикация: `pr-analyst` →
  `pr-calculator`. Покажи балл и разложение формулы.
- **«Фрейя, запусти пайплайн»** — все статьи из `data/articles/` по порядку:
  1) `pr-analyst` по каждой → JSON-разборы;
  2) `pr-calculator` по каждому разбору → PR Points (через `scripts/calc_pr_points.py`);
  3) `pr-reporter` по всем расчётам → `output/pr-report.md`.
- **«Фрейя, сделай сводку»** — только шаг 3 по уже посчитанным статьям.

### Полный цикл одной командой
- **«Валькирии, полный цикл по теме X»** — прогон связки Хильда → Сага одним
  запросом. Выполняй по шагам, останавливаясь и показывая результат каждого:
  1. **Хильда:** найди и квалифицируй повод по теме X, оформи бриф. Присвой
     брифу `id` вида `rel-<дата>-<slug>` — он же станет тегом кампании.
  2. **Покажи бриф оператору** (повод, угол, приоритет) и продолжай.
  3. **Сага:** адаптируй этот бриф — 4 версии под СМИ с проверкой уникальности,
     сохрани тексты + `summary.json`.
  4. **Покажи сводку:** какой повод нашли и какие версии готовы (с уникальностью).

  Шаг Фрейи в этот цикл НЕ включай по умолчанию: она оценивает реальные выходы
  СМИ, которых в момент ньюсджекинга ещё нет. Если оператор явно просит
  («…и оцени выходы») И в `data/articles/` уже есть публикации с тем же тегом
  `Кампания: <id брифа>` — добавь шаг: запусти Фрейю по этим выходам и покажи
  сводку по кампании. Если выходов с этим тегом нет — так и скажи, Фрейю не вызывай.

  Важно: если на каком-то шаге внешний сервис (поиск, text.ru) не отвечает —
  остановись, сообщи на каком шаге, и не обрушивай весь прогон.

### Демо-прогон для показа (стабильный, без живых внешних вызовов)
- **«Валькирии, демо-прогон по кампании <id>»** — показывает всю цепочку из трёх
  агентов на заранее подготовленных данных. Ничего не ищет в интернете и не дёргает
  text.ru, поэтому безопасен для живой демонстрации. По шагам:
  1. **Хильда (показ готового):** найди и покажи бриф этой кампании из `output/briefs/`
     (или подготовленный файл брифа). НЕ запускай новый поиск — бери готовое.
  2. **Сага (показ готового):** покажи 4 версии и их уникальность из
     `output/<brief_id>/summary.json`. НЕ перегенерируй версии и НЕ обращайся к text.ru —
     показываешь заранее посчитанный результат.
  3. **Фрейя (живой расчёт):** обработай ВСЕ файлы в `data/articles/`, у которых в шапке
     стоит `Кампания: <id>` — ровно их, не выбирая ничего сам и не подтягивая другие.
     Прогон: `pr-analyst` → `pr-calculator` → `pr-reporter`. Этот шаг можно считать вживую:
     он использует только чтение файлов и локальный скрипт, без внешних сервисов.
  4. **Покажи итог:** бриф → версии → отчёт с разделом «Эффект по кампании <id>»
     (число выходов и суммарный PR Points).

  Набор статей для шага 3 определяется ТОЛЬКО тегом `Кампания: <id>`: обрабатываются
  все файлы с этим тегом и никакие другие. Что попадёт в прогон — решаешь ты тем, какие
  файлы пометишь этим id.

## Структура и конфигурация

```
.claude/agents/   hilda, saga-adapter, pr-analyst, pr-calculator, pr-reporter
config/           outlets.md (вес N), key-messages.md, scoring-config.md (MQI),
                  media-profiles/ (стиль 4 СМИ для Саги)
scripts/          calc_pr_points.py (детерминированный расчёт PR Points)
data/articles/    входные статьи для Фрейи (только примеры в репозитории)
output/           брифы, summary.json, pr-report.md
dashboard/        index.html — витрина над результатами
```

Меняешь критерии — правишь файлы в `config/`, код агентов и скрипта не трогаешь.
При изменении коэффициентов MQI синхронизируй `config/scoring-config.md` и
`scripts/calc_pr_points.py`.

## Принципы

- Анализ и расчёт у Фрейи разделены: смысл оценивает модель, арифметику — код
  (воспроизводимость от недели к неделе).
- Изоляция контекста: разбор каждой статьи живёт в субагенте, не засоряет
  основной разговор; наверх возвращается только сводка.
- PR Points — порядковая шкала (динамика, больше/меньше), не точное измерение.

## Безопасность

- Все ключи, токены, адреса и пути — только через переменные окружения
  (`.env`, шаблон в `.env.example`). В коде и промптах реальных значений нет.
- Адрес рассылки Хильды берётся из `OPERATOR_EMAIL`.
- `.env`, учётки, файлы Memory, артефакты `output/` и чужие тексты статей — в
  `.gitignore`. Полные тексты публикаций в репозиторий не коммитятся.
- Лимит расходов выставлен в консоли Anthropic.
