# PR-ньюсрум «Валькирии» — рецепт воспроизведения

Это инструкция, как собрать с нуля рабочий PR-ньюсрум, состоящий из трёх Claude Code
субагентов и витрины-дашборда. Следуй шагам по порядку. Файлы-заготовки лежат рядом со
скиллом в папках `agents/`, `config/`, `dashboard/` — на них есть ссылки в тексте.

## Что это и зачем

Сквозной PR-конвейер для PR-отдела: ловит инфоповоды → переупаковывает материал под
4 СМИ с проверкой уникальности → оценивает вышедшие публикации по медиаэффективности.
Над результатами — единый дашборд. Цель — заменить ручную работу в файлах и почте одним
наглядным процессом.

## Архитектура

```
Хильда (newsjacking)  →  Сага (адаптация)  →  [публикация]  →  Фрейя (PR Points)
   находит и                делает 4 версии                      оценивает выходы
   приоритизирует           под СМИ + уникальность                и строит рейтинг
        │                         │                                     │
        └──────────────── всё стекается в дашборд ────────────────────┘
```

Важно: субагенты Claude Code **не вызывают друг друга**. Последовательность задаёт главная
сессия по инструкции в `CLAUDE.md`. Дашборд — отдельный статический фронтенд, который
**читает результаты** прогонов, а не запускает агентов в браузере.

## Структура проекта

```
pr-newsroom/
├── CLAUDE.md                  # оркестрация: какие команды → какая последовательность агентов
├── .claude/agents/
│   ├── hilda.md               # newsjacking-скаут (Sonnet)
│   ├── saga-adapter.md        # адаптер под 4 СМИ + text.ru (Sonnet)
│   ├── pr-analyst.md          # Фрейя, шаг 1: анализ публикации (Sonnet, read-only)
│   ├── pr-calculator.md       # Фрейя, шаг 2: расчёт PR Points (Haiku + Bash)
│   └── pr-reporter.md         # Фрейя, шаг 3: сводный отчёт (Sonnet + Write)
├── config/
│   ├── outlets.md             # справочник изданий → вес N
│   ├── key-messages.md        # ключевые сообщения бренда + конкуренты
│   ├── scoring-config.md      # коэффициенты MQI (синхронны со скриптом)
│   └── media-profiles/        # профили стиля 4 СМИ (для Саги)
├── scripts/
│   └── calc_pr_points.py      # детерминированный расчёт PR Points (арифметика — код)
├── data/articles/             # статьи для Фрейи (full_*.txt — локально, example_*.txt — в репозиторий)
├── output/                    # отчёты Фрейи + адаптации Саги (артефакты прогонов)
├── dashboard/
│   └── index.html             # витрина: 3 блока на демо-данных, потом — на реальных
├── .env.example               # шаблон секретов
└── .gitignore
```

## Шаг 1. Развернуть пайплайн агентов

1. Скопируй заготовки из `agents/` этого скилла в `.claude/agents/` проекта, а `config/`
   и `scripts/` — в корень. Запусти Claude Code в папке проекта: `claude`. Проверь, что
   субагенты подхватились: `/agents`.
2. Три роли Фрейи (анализ → расчёт → отчёт) уже разделены намеренно: смысл оценивает
   модель, арифметику — детерминированный скрипт `calc_pr_points.py`. Это даёт
   воспроизводимость от недели к неделе. Не объединяй их в один промпт.
3. Сага сокращена до 4 СМИ (Forbes Russia, РБК Компании, Инк, Setters Media) и проверяет
   уникальность через API text.ru с ручным фоллбэком. Профили стиля СМИ лежат в Memory MCP
   под ключами `media_profile:<id>` либо в `config/media-profiles/`.
4. Хильда квалифицирует поводы по чек-листу из 6 критериев и присваивает приоритет
   (срочно / важно). Она ничего не публикует — только готовит брифы и сводки.
5. Фрейя умеет привязывать публикации к релизу/кампании: статья помечается строкой
   `Кампания: <id>`, поле `campaign` проходит сквозь все три роли, и `pr-reporter`
   сворачивает PR Points по релизу (раздел «Эффект по кампаниям»). Формула расчёта
   при этом не меняется — поле необязательное и обратносовместимое.

## Шаг 2. Настроить окружение и секреты

Создай `.env` на основе `.env.example`. Минимальный набор:

```
ANTHROPIC_API_KEY=...          # для агентов и (опц.) дашборда
TEXTRU_API_KEY=...             # проверка уникальности у Саги
GDRIVE_OUTPUT_FOLDER_ID=...    # папка для адаптаций Саги
OPERATOR_EMAIL=operator@example.com   # адрес для рассылок Хильды — подставь свой
BRAVE_API_KEY=...              # веб-поиск Хильды (или TAVILY_API_KEY)
```

В промптах и конфигах **не должно быть зашитых адресов, ключей и путей** — всё через
переменные. Адрес рассылки Хильды берётся только из `OPERATOR_EMAIL`.

## Шаг 3. Прогнать пайплайн и получить артефакты

Команды главной сессии (см. `CLAUDE.md`):

- `Хильда, найди поводы по теме X` → брифы с приоритетом в `output/briefs/`.
- `Сага, адаптируй бриф <id>` → 4 версии под СМИ + `summary.json` с уникальностью.
- `Фрейя, запусти пайплайн` → `output/pr-report.md` с рейтингом PR Points.
- `Валькирии, полный цикл по теме X` → одной командой Хильда → Сага (повод → 4 версии),
  пошагово с показом результата каждого шага. Бриф получает `id`, который служит тегом
  кампании. Фрейя в цикл не входит по умолчанию (она про реальные выходы, которых ещё нет);
  подключается отдельно, если в `data/articles/` уже есть публикации с тем же тегом
  `Кампания: <id>`.

Чтобы связать релиз и его выходы для Фрейи, ставь в шапке файлов-выходов одинаковую
строку `Кампания: <id брифа/релиза>`.

Эти артефакты (брифы, `summary.json`, отчёт) — то, что показывает дашборд.

## Шаг 4. Поднять дашборд

1. Открой `dashboard/index.html` в браузере — он сразу работает на демо-данных
   (объект `DATA` в начале скрипта). Сборка и установка не нужны.
2. Демо-данные построены в форматах реальных артефактов (см. «Форматы» ниже). Чтобы
   перейти на настоящие прогоны, замени объект `DATA` на чтение файлов из `output/`
   (брифы Хильды, `summary.json` Саги, разбор отчёта Фрейи).
3. Оставь видимый бейдж «демо-режим», когда показываешь на тестовых данных — это честно
   и снимает риск «не загрузилось» на живой демонстрации.

## Шаг 5. Деплой и публикация на GitHub

- Деплой: `dashboard/index.html` заливается на Vercel или GitHub Pages как статика — без
  сборки, получаешь живую ссылку.
- В репозиторий кладёшь код, `.env.example`, `.gitignore` и `README.md` с инструкцией
  запуска и пользовательским сценарием.

## Безопасность (обязательно перед публикацией)

- `.env`, `secrets/`, `*.key`, `*.pem`, файлы Memory (`*.json` с данными) — в `.gitignore`.
- Никаких реальных ключей, токенов и личных адресов в промптах и истории коммитов. Если
  ключ всё же попал в историю — почистить (`git filter-repo`) и перевыпустить ключ.
- **Тексты публикаций — два слоя.** Полные тексты держи только локально
  (`data/articles/full_*.txt`, исключены `.gitignore`) — на них Фрейя делает точный
  анализ. В репозиторий идут только выдержки `example_*.txt` (шапка «Источник / дата /
  ссылка / Кампания» + дословная выдержка 3–5 предложений + 1–2 предложения пересказа
  своими словами + ссылка) и сам отчёт `output/pr-report.md` (его публиковать можно — это
  аналитический продукт, а не перепечатка чужих статей). Пресс-релизы компании как исходник
  безопасны — они создаются для распространения.
- Поставь лимит расходов в консоли Anthropic, чтобы случайно не получить большой счёт.

## Форматы данных (связь агентов и дашборда)

Дашборд ждёт эти структуры:

**Бриф Хильды** — поля: `id`, `title`, `priority` (`urgent` | `important`), суть, угол,
окно реакции, источник.

**`summary.json` Саги** — `brief_id` + массив `results`, в каждом: `media_id`, `media_name`,
`status` (`ready` | `manual` | `failed`), `final_uniqueness` (0–100), `iterations`.

**Отчёт Фрейи** — по каждому субъекту: название, суммарный PR Points, число публикаций,
флаг «это Зерокодер». Рейтинг строится по убыванию суммарных PR Points. Дополнительно —
раздел «Эффект по кампаниям»: по каждому тегу `Кампания` число выходов и суммарный
PR Points. Файлы-статьи на входе несут в шапке `Источник: <издание>` и необязательную
`Кампания: <id>`.

PR Points = N × MQI (методика Skyeng, адаптированная). Это порядковая шкала
(больше/меньше, динамика), а не точное измерение — отрази это и в отчёте, и на дашборде.
